1 · The big picture

There are three layers. The browser shows the page. The PHP scripts on the PolyU server decide what's allowed. The database remembers everything.

Front end

runs in the visitor's browser

This repo. index.html is the page, main.js and booking.js make it interactive, api.js is the only file that sends requests out.

PHP backend

runs on www.polyu.edu.hk

Folder iemakerlab/ (not in git). Checks who you are, applies the booking rules, reads and writes the database, sends emails.

MySQL database

separate server, 158.132.152.154

Database iciemakerlab_external. Tables hold bookings, timeslots, printers and training records.

Browser → fetch() over HTTPS with a login cookie → PHP → SQL → MySQL, and the answer travels back as JSON.

The rule that explains the design: the browser is untrusted. Anyone can open DevTools and change any JavaScript. So the JavaScript only draws the screen and asks nicely. The PHP re-checks everything (are you logged in, are you trained, is the slot free). Keep that in mind when you read the security section.

2 · How to read this code

Function
A named block of steps. function bkToday() { ... } defines it; bkToday() runs it.
const / let
A named box that holds a value. const never gets reassigned, let can be.
async / await
Network calls take time. await means "pause here until the server answers", and only works inside an async function. When you see await on a line, that line is waiting for something slow, usually the server.
try { } catch (err) { }
Try the risky steps. If any throws an error, jump to catch and handle it instead of crashing. Almost every server call is wrapped like this.
import / export
How files share functions. main.js imports from api.js, so it can call getSession().
Naming prefixes in booking.js
bk… desktop booking, bkp… phone booking, tk… ticket popup. In main.js, mpop… is the desktop machine popup and mpopm… the phone one.

4 · api.js, the bridge

Every other file calls these functions and never writes fetch itself. That keeps the server details in one place. The file has two halves: the real client, and a mock (fake) server used when you test off the PolyU domain.

The switch between real and fake

api.jstop of file
const BOOKING_ROOT = '/ic/iemakerlab/booking';const API_ROOT = `${BOOKING_ROOT}/api`;export const USE_MOCK = !ON_POLYU;← the on/off switch

If the page isn't on polyu.edu.hk, USE_MOCK is true and no network request is ever sent. That's why everything works on your laptop.

request(method, path, body), the one real network call

api.jsfunction request

JSON.stringify(body) : undefined,  });  let json = null;  try { json = await res.json(); } catch { /* not JSON, e.g. an SSO login page */ }  if (!res.ok || !json) {    throw new ApiError(json?.Message || json?.message || `Request failed (${res.status})`, res.status);  }  return json;}
  • fetch(...) is the browser's built-in "send an HTTP request". The URL becomes e.g. /ic/iemakerlab/booking/api/3Dprinter/MyBooking.php.
  • credentials: 'include' makes the browser attach the access_token cookie. That cookie is your proof of login. Without it the server answers 401.
  • If the server replies with an error code, or something that isn't JSON, the function throws an ApiError carrying the server's Message. Later code shows that message in an alert(). That's how users see "session full" or "already booked".

The front end never sends who you are. It sends only what you want to book. The server works out who you are from the cookie. That's the right design, and it's why the security story is mostly good.

The three small translators

toBooking(row)
The server's field names are awkward (service_timeslot_display, cancel_booking_allow). This renames them to tidy ones (label, canCancel) so the rest of the code stays readable.
toAvailability(json)
Same idea for printerStatus.php: turns 'Available Date' and '3D Printer' into { dates, printers: [{ type, sessions }] }. Each session has a status of Available, Full or Unavailable.
getTrainingStatus()
Calls getAvailability() and sees whether it throws "Not Trained User". Returns { printer: true } or { printer: false }.

The mock server

The big const mock = (() => { ... })() block at the bottom pretends to be PHP. It stores a fake login and bookings in localStorage (the browser's small notepad), invents two printers and three daily sessions, and returns the same shapes the real server does. It also re-implements a few of the real rules (no double booking, session full, cancel cutoff) so the UI can be tested. It is not used on the live site.

7 · The PHP backend

PHP code runs on the server each time a request arrives. It runs top to bottom, then whatever it echos is sent back. The five files that matter, in the order a request hits them:

  1. authorization.php: who are you? Reads the access_token cookie, verifies the signature and expiry with PolyU's ADFS login service, and sets $user_id (staff number, or NetID). Bad or missing token → HTTP 401 and stop.
  2. db_connect.php: open the database. Reads host, user, password and name from .env and connects with mysqli.
  3. general_function.php: shared helpers. CheckUserTrained(), GetAllowDate(), GetTimeslot(), GetPrinterInfo(), HandleError() and so on.
  4. printerStatus.php: read-only availability. GET only. Loops printers × dates × sessions and marks each Available / Full / Unavailable.
  5. MyBooking.php: the main one. One file, three behaviours chosen by HTTP method: GET lists, POST creates, DELETE cancels.

GET and DELETE

  • GET selects this user's rows from 3d_print_booking_record (WHERE user_id = ?, from the day before today onward), then adds service_timeslot_display and cancel_booking_allow (1 only if the session hasn't ended and status is 0).
  • DELETE validates the JSON, rejects duplicate IDs, then checkDeleteBookingExist() confirms the booking belongs to this user, is status 0, and the session hasn't ended. Then deleteBooking() does UPDATE ... SET status = 2 (a soft delete: the row stays) and sends a cancellation email.

8 · One booking, start to end

  1. You open the site. main.js runs startSession().
  2. Server: GET api/session.php → {logged_in:false}. Header shows "Login".
  3. You click Login. login() sends the whole browser to /ic/iemakerlab/booking/, which redirects to PolyU SSO.
  4. Server: you sign in on the PolyU page. polyusso/callback.php swaps the code for tokens and sets the access_token cookie (HttpOnly, Secure), then redirects to SSO_LANDING_PAGE.
  5. The page loads again. startSession() now gets logged_in:true, loads your bookings, checks training, draws the badges.
  6. You click a machine, then Book now. openBookingFlow() → bkLoadAvailability().
  7. Server: GET printerStatus.php. If untrained → 401 "Not Trained User" → training popup. Otherwise dates and sessions come back and the week strip is drawn.
  8. You pick a date and up to 3 sessions, tick the safety box, press Confirm. bkConfirmBooking() runs.
  9. Server: POST MyBooking.php with {"New Booking":[{service_date, service_timeslot_id, printer_type}]}. PHP runs the 8 checks, inserts rows, sends the email, replies "New Booking Added".
  10. Server: GET MyBooking.php to reload. The ticket appears in the hero section.
  11. Server: Cancel → DELETE MyBooking.php with the booking ID → status 2, email sent, list reloaded.

9 · Security considerations

I read the front end and the PHP files in iemakerlab/booking/. I did not test against a live server or attack anything, so these come from reading the code. Severity is my judgement of the risk once the site is live.

What is already done well

  • Identity comes from the token, never from the request. The browser never sends a user ID, so you can't ask for someone else's bookings by changing a number.
  • Ownership is checked on cancel. checkDeleteBookingExist and deleteBooking both include AND user_id = ?, so guessing a booking ID gets you "not found".
  • SQL is mostly parameterised. prepare() + bind_param() keeps user input out of the SQL text (one exception, M3).
  • Training and booking rules are enforced on the server. Editing the front end can't skip them.
  • The login cookie is HttpOnly and Secure. JavaScript on the page can't read it, and it's only sent over HTTPS.
  • Secrets stay out of git. iemakerlab/ is in .gitignore, and .htaccess denies web access to .env, db_connect.php, authorization.php and other internals.
  • Output escaping exists. bkEsc() is used when server text goes into innerHTML, and error text goes into alert(), which is plain text.
  • Cancelled bookings are soft-deleted, so there's an audit trail.
Status: fixed in code. H1, M1, M2, M3, L1 and L3 have been changed (see the notes under each). They are changed in your local iemakerlab/ copy and in this repo, not on the PolyU server yet. The backend files must be handed to the server owner. M2 caps each request at 3 sessions; a per-user total cap is a policy decision I left alone. L2 and L4 need no code change.

Findings, most important first

HIGH H1 · Cross-site request forgery on book and cancel

What: The login cookie is set with SameSite=None (callback.php), which means the browser sends it even when the request starts from another website. MyBooking.php reads the body with file_get_contents('php://input') and json_decodes it without checking the Content-Type header, and it has no CSRF token.

Attack: A malicious page can make a logged-in student's browser send a text/plain POST containing the JSON. That kind of request needs no CORS permission, so no browser block applies, and the cookie rides along. Result: bookings made or cancelled without the student knowing.

Fix (backend): in MyBooking.php reject any POST/DELETE whose Content-Type isn't application/json (this forces a CORS preflight that other sites fail), and/or check that the Origin header is https://www.polyu.edu.hk. Also ask whether the access_token cookie really needs SameSite=None; Lax would block this attack outright, and since your front end is same-origin it should work.

MEDIUM M1 · Two people can take the last printer at the same time

What: POST checks isSessionFull() in one step, then inserts in a later step, with no database transaction or lock between them. Two requests arriving together both see "1 slot left", and both insert.

Fix (backend): wrap the check and insert in a transaction using SELECT ... FOR UPDATE on the relevant rows, or add a database-level constraint.

MEDIUM M2 · "Max 3 sessions" is only enforced in the browser

What: The README says so too: it's a front-end rule. The server loops over every item in New Booking with no count limit. Anyone using a script or DevTools can post dozens of items, and there's no rate limit, so one trained user could hold many sessions.

Fix (backend): reject payloads over 3 items, and count the user's existing active bookings per date/week against a cap.

MEDIUM M3 · Internal error text is sent to the browser

What: Many error paths return $conn->error or $stmt->error (raw MySQL messages), and authorization.php returns error_detail => $e->getMessage() for invalid tokens. The front end shows Message in an alert(), so users could see table or column names. That helps an attacker.

Also: insertBooking() puts $booking_id directly into the SQL string instead of binding it. It's safe today because the server generates it, but it breaks the "always bind" habit and would become injectable if the code ever changes.

Fix: log the detail on the server, return a generic message. Bind booking_id like the other values.

LOW L1 · ?mock works on the live site

What: USE_MOCK is true if the URL has ?mock, even on polyu.edu.hk. It can't harm the server, because no request is sent. But someone could send a student a ?mock link, let them "book" a session that only exists in their own browser, and they'd miss their real slot.

Fix: only honour ?mock when the hostname isn't polyu.edu.hk. One-line change in api.js.

LOW L2 · Keep HTML escaping tight as the code grows

What: booking.js builds HTML strings and assigns them via innerHTML in 13 places, main.js in 20. The server-supplied text I traced (printer name, session label, status) goes through bkEsc(), so I found no hole. But the front end is served from the same origin as the API with the login cookie, so any future XSS bug would let an attacker book and cancel as the victim.

Fix: always pass server strings through bkEsc() (or use textContent) and consider adding a Content-Security-Policy header on the server.

10 · Glossary

API / endpoint
A URL a program (not a person) calls to get or change data. printerStatus.php is an endpoint.
JSON
Text format for data, like {"Status":"Success"}. What the front end and PHP use to talk to each other.
HTTP methods
GET reads, POST creates, DELETE removes. Codes: 200 ok, 400 you asked wrong, 401 not logged in or not allowed, 405 wrong method, 500 server broke.
Cookie
A small value the server asks the browser to store and send back on every request. access_token is your login proof.
SSO
Single sign-on. You log in once on PolyU's official page and the site trusts that.
Token / JWT
A signed note from the login system saying who you are and until when. PHP verifies the signature.
SQL / prepared statement
The language for asking the database things. A prepared statement uses ? placeholders so user input can't be run as SQL.
CSRF
Another website tricking your browser into sending a request to this site, using your cookie.
XSS
Getting a page to run attacker-written JavaScript, usually via unescaped text placed in HTML.
Same origin
Same protocol, domain and port. The front end must be on www.polyu.edu.hk for the cookie to work.
Mock
A fake stand-in for the real server, for testing.
localStorage
A small per-site notepad inside the browser. Only the mock uses it.
